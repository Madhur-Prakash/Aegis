# Data

Everything the models see is **synthetic and generated by code in this repository**. Nothing was
scraped, purchased or copied from a real counterparty. Regenerate all of it with:

```bash
cd backend && uv run python -m scripts.generate_dataset --seed 42
```

Deterministic: the same seed produces byte-identical output.

---

## 1. What gets generated

| artifact | contents |
|---|---|
| `data/generated/deals.parquet` | **2,000 deals** with features, a `deal_went_bad` label and a `train`/`valid`/`test` split |
| `data/generated/evidence/` | **150 labelled evidence bundles** with real PDFs (real text layer) and real PNGs (real pixels) |
| `data/generated/calibration/` | **120 bundles from a different seed (43)**, used only to fit the confidence map |
| `data/generated/counterparties.json` | **30 entities**, 4 of them thin-file |
| `data/fixtures/demo_deal.json` + `demo_evidence/` | the exact demo deal, so `make demo` is reproducible |

### Why the calibration corpus is separate

The confidence map is fitted with isotonic regression on `calibration/`, generated with **seed 43**.
The 150 evaluation bundles in `evidence/` (seed 42) are never touched by fitting, so Suite A is a
genuine held-out measurement rather than a fit reported as an evaluation. Measured for the recorded
run: 120 calibration bundles, release rate 0.6417, raw score range 0.0–0.988, class-separable with
anchors `r0 = 0.816167` and `r1 = 0.979`.

### The documents are real documents

`scripts/docgen.py` renders PDFs with ReportLab (a real text layer that `pypdf` genuinely parses)
and PNGs with Pillow (real pixels, real blur when a scan is meant to be poor). The extraction and
image-analysis paths are therefore actually exercised. This matters: the image analyser originally
reported the **backdrop** colour as the garment colour, which only surfaced because the pixels were
real. It now extracts a palette and identifies the subject colour by excluding backdrop luma/chroma
(`BACKDROP_LUMA = 70`, `BACKDROP_CHROMA = 26`).

## 2. Base rates — every one declared

Marked `[sourced]` if it comes from a published figure, `[assumed]` if it is a judgement call. Every
rate below is `[assumed]`, and this document says so rather than implying provenance that does not
exist.

| constant | value | status | reasoning |
|---|---|---|---|
| `BASE_DISPUTE_RATE` | **0.11** | `[assumed]` | Deliberately higher than most B2B escrow reporting. A generator that disputes rarely makes the risk model look better than it is. |
| `THIN_FILE_SHARE` | **0.18** | `[assumed]` | The share of counterparties with no completed-deal history. Thin-file cases are where a risk model is most tempted to guess, so they are over-represented rather than under. |
| `ON_TIME_MEAN` | **0.88** | `[assumed]` | Mean on-time delivery rate, σ ≈ 0.09, clipped to [0.4, 1.0]. |
| `STRETCH_RISK_KNEE` | **1.5** | `[assumed]` | A deal above 1.5× a seller's largest previous deal is treated as a stretch. The knee is a modelling choice, not an observation. |
| Corpus bad rate | **18.4% train / 18.0% test** | measured | An output of the generator below, not an input. |

### The generative model behind `deal_went_bad`

A smooth logistic function of the features, not a lookup table, so the risk model has something real
to learn and the logistic baseline is a fair comparison:

```python
z  = -1.30
z += -0.045 * min(deals_completed, 40)
z +=  2.2   * dispute_rate
z += -1.2   * (on_time_rate - 0.88)
z +=  0.55  * max(0.0, stretch_ratio - 1.5)
z += -1.3   * (objectivity - 0.60)
z += -0.0009 * min(age_days, 1200)
z += -0.06  * (min(milestone_count, 8) - 3)
p  = 1 / (1 + exp(-z))
```

Terms are centred on the corpus means so the intercept alone sets the base rate.

**This is published for a reason.** Because the generator is logistic in exactly these features, the
logistic model is *correctly specified* and the gradient-boosted model has nothing extra to exploit —
which is why LightGBM loses (test AUC 0.7261 vs 0.7435). That is a property of the corpus, not
evidence that boosting is a bad choice on real data, and the README says so instead of presenting the
baseline win as a triumph.

### Features the risk model sees

`deals_completed`, `gmv_paise`, `disputes_raised`, `dispute_rate`, `on_time_rate`,
`largest_deal_paise`, `deal_paise`, `milestone_count`, `counterparty_age_days`,
`condition_objectivity_score`, `stretch_ratio`, `log_gmv`, `avg_milestone_paise`, `category_code`.

`condition_objectivity_score` (mean 0.62, σ 0.2) is the share of clauses that are machine-checkable.
It is a feature because a deal whose conditions are mostly subjective is genuinely riskier to
automate, and the demo's top-three factors include it: *"92% of clauses are machine-checkable",
factor −0.963*.

Split: 1,400 train / 300 valid / 300 test. **The test split is scored exactly once**, at the end.
Hyperparameters and the choice between the two models are decided on validation only.

## 3. The 150 evaluation bundles

100 clean, 50 adversarial. Every adversarial bundle belongs to exactly one category, and every
category is reported separately in `RESULTS.md` — an aggregate accuracy can hide a category that
fails completely.

| category | n | what it tests |
|---|---|---|
| `clean` | 100 | The evidence supports the clause. Releasing is correct. |
| `wrong_date` | 8 | A document dated outside the milestone window. |
| `altered_amount` | 7 | A total edited after issue. |
| `right_type_wrong_milestone` | 7 | A genuine document for a *different* milestone. |
| `fabricated_totals` | 7 | Line items that do not sum to the stated total. |
| `low_quality_scan` | 7 | A genuinely blurred scan — extraction quality drops for real. |
| `photos_cannot_establish_quantity` | 7 | Four photographs cannot evidence a count of 500. **The correct answer is `UNVERIFIABLE` → escalate, not reject.** |
| `valid_but_unusual` | 7 | Odd but legitimate. Rejecting these is the failure mode. |

Labels are derived from the **evidence**, following the same published rubric the prose prompt
describes — so a correct pipeline can reach them and an incorrect one cannot be rescued by the label.
The fixture provider has no access to the labels.

`photos_cannot_establish_quantity` and `valid_but_unusual` exist to keep the system honest in both
directions: a system that escalates everything scores well on adversarial cases and is worthless, and
a system that rejects anything unusual punishes honest sellers.

## 4. Counterparties

30 entities, 4 of them thin-file, spanning `apparel`, `electronics`, `industrial`, `agri`, `services` and
`packaging`. Names, cities and GSTINs are invented. No real business appears anywhere in this
repository.

The pricing tier distribution over the 2,000-deal portfolio, measured:

| tier | deals | share | observed bad rate | fee % | hold days | prefund % |
|---|---|---|---|---|---|---|
| TIER_1 | 1093 | 54.6% | 4.7% | 0.8 | 0 | 30 |
| TIER_2 | 338 | 16.9% | 17.5% | 1.5 | 3 | 50 |
| TIER_3 | 417 | 20.8% | 36.0% | 2.5 | 7 | 100 |
| DECLINE | 152 | 7.6% | 67.1% | — | — | — |

The observed bad rate rises monotonically with tier, which is the only property that makes the tiers
mean anything.

## 5. Personal data

There is none. Every name, email address, phone number, GSTIN and bank reference in the corpus and
the seed is invented. Demo accounts use `@meridian.demo` and `@tirupur.demo`, which cannot receive
mail.

Artifact bytes are **never logged and never sent on chain** (I7, I11). Access is tenant-scoped (I12)
through short-lived HMAC presigned URLs; there is no public path to an artifact.

## 6. Reproducing

```bash
cd backend
uv run python -m scripts.generate_dataset --seed 42   # the corpus
uv run python -m evals.run_all                        # every metric
```

Delete `backend/evals/out/` and re-run: the JSON files are identical apart from timing fields, which
are marked as such in `evals/run_all.py` (`latency_ms`, `wall_ms`, `mean_latency_ms`, `p50`, `p95`,
`max`).
